# Admin account — план для #41

## Согласованные решения

- Один аккаунт администратора, без управления другими администраторами.
- Только телефон: взрослый рабочий интерфейс, компактные списки, отдельные страницы больших форм, bottom sheet для коротких действий. Не более 1–3 крупных карточек на странице, без uppercase. Украинская локализация.
- Управление преподавателями, учениками, группами, курсами и категориями, балансом, самостоятельным стриком и каталогом наград.
- Настройки: имя/роль, анимации, выход.
- Единственный admin уже существует, пароль фиксирован. Создание admin и смена пароля не входят в задачу; пароль не помещать в клиентский код.
- Архив исключён из первой версии: без кнопок, снимков, таблиц и восстановления.
- Блокировка и разблокировка учеников исключены.
- Расписание, занятия, замены, посещаемость и обзор проблем исключены. Стрик не связан с посещаемостью.
- Выдача наград не относится к нашей ответственности: исключены выдача/отмена, очередь выдачи, склад, возвраты, покупка со списанием монет, использование и сроки выданных привилегий. Остаётся каталог, включая позиции типа privilege.
- Заметки и произвольные метки не входят в согласованный объём.
- Журнал действий отложен целиком: не реализовывать хранение логов в PostgreSQL, таблицы событий, UI журнала или отдельную инфраструктуру логирования. Выбор хранилища для будущего журнала — отдельное решение.
- Вместе с журналом убрать автоматическое сохранение версий при каждом действии, начальный импорт, сравнение версий, фоновую сверку и принудительный перевод teacher-флоу на actions ради аудита.
- История финансовых транзакций из существующего API остаётся: это функция баланса, а не новый журнал логов.
- Реализацию пока не начинать: документ фиксирует план.

## Правило подключения

1. Есть endpoint основного API — подключить реальную операцию.
2. Независимые данные приложения — server function и наша БД.
3. Нужно изменить основную систему, но endpoint отсутствует — полноценная форма, валидация, подтверждение при необходимости и локальный результат без вызова отсутствующей мутации. Не придумывать URL и не выдавать демонстрационные изменения за сохранённые.

Наличие UI неподключённой операции не означает завершённую backend-функциональность или готовность закрыть #41.

## Наша БД и граница возможностей

- В проекте подключены PostgreSQL, Drizzle и `postgres`: `src/db/index.ts`, `drizzle.config.ts`. На момент исследования схема и миграции отсутствовали; соединение с реальной БД в рамках планирования не проверялось.
- Основной API владеет аккаунтами, ролями, сессиями, кодами доступа, курсами, группами, членством, балансами, транзакциями, стриками и базовым каталогом.
- Дополнительная БД доступна для будущих независимых функций. Само подключение не требует создавать таблицы: в первой версии не строить копию основного каталога или систему архивирования.
- Базы независимы: нет общей транзакции или межбазовых FK. Внешние ID — логические ссылки; user ID и profile ID не смешивать.

| Область             | Реализуем сейчас                                                       | Чего дополнительная БД не позволяет                                        |
| ------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Люди, группы, курсы | Существующие API-операции                                              | Изменять/удалять основные поля и объекты без endpoints                     |
| Доступ              | Вход/выход, доступные операции кодов учеников                          | Сбрасывать код преподавателя, отзывать сессии, менять admin-пароль без API |
| Баланс              | Операции по причинам, отмена, история, массовая обработка              | Произвольная сумма, новые причины и изменение серверных тарифов            |
| Стрик               | Просмотр, запуск, завершение, изменение дней через API                 | Придумывать новые серверные правила стрика                                 |
| Каталог             | Доступные API-операции, UI управления и изображения по ссылке/из файла | Изменять неподдерживаемые поля API или сохранять файл без storage          |
| Категории           | Использовать текущий enum                                              | Расширять enum основного API                                               |

## Server functions и hooks

- Серверные функции — slice `actions`; в file-based routes `-actions/` с `index.ts`.
- Хуки TanStack Query для actions — `hooks/actions`, в routes `-hooks/actions/` с `index.ts`.
- Нейминг `useXAction`, например `useCreateRewardAction`, если для операции действительно нужна server function.
- Пока не разделять hooks на queries/mutations slices. Внутри применять `useQuery` для чтения и `useMutation` для записи.
- Page model сохраняет результат hook целиком и возвращает его в `queries` или `mutations`.
- Локальное поведение держать у страницы, общее — у ближайшего общего родителя. Generated hooks основного API можно продолжать использовать; не оборачивать все endpoints в actions без необходимости.
- Drizzle и секреты доступны только серверу. Каждая action проверяет вход, актуальную сессию и разрешённую роль; route guard не заменяет серверную проверку.
- Для вызова основного API на сервере передавать сессию текущего пользователя существующим cookie forwarding. Не доверять actor ID/роли из клиента.
- Существующие teacher-флоу не переделывать ради отложенного логирования.
- Массовые API-операции показывают результат по каждому объекту. Не повторять автоматически финансовые операции с неизвестным результатом после timeout; общей транзакции между системами нет.

## Области управления

### Вход и настройки

- `/login` → `/admin`, сессия через `/auth/me`, выход через `/auth/logout`.
- Добавить admin в redirects, guards и навигацию; устранить возможные циклы `/` ↔ `/group`, централизовать домашний маршрут по роли.
- Настройки: имя, роль, анимации, выход. `/auth/me/credentials` запрашивать только для ученика.
- Поле входа `code` допускает до 128 символов. Использовать существующий admin и его фиксированный пароль через общий вход; флоу создания/смены пароля не нужен.

### Преподаватели

- Список/поиск: `/users` с фильтром роли; профиль: `/teacher/{teacher_id}`.
- Регистрация: `POST /teacher/register`; результат с кодом и копированием.
- Назначение и снятие с групп: `PUT /group/id/{group_id}/teachers`, максимум два user IDs.
- Редактирование имени, удаление, сброс кода, блокировка/разблокировка преподавателя и отзыв сессий: UI без отсутствующих mutations. Исключение блокировки относится к ученикам.
- При удалении показать связанные группы; переназначения — отдельные реальные API-операции.

### Ученики

- Список, поиск, профиль: `/student`, `/student/{student_id}`.
- Регистрация: `/student/register`, имя, аватар, минимум одна группа; экран выданного кода.
- Nickname и аватар: существующие PATCH endpoints; не считать nickname отдельным полным именем без уточнения контракта.
- Группы: добавление, отчисление, перевод и дополнительные группы.
- Просмотр/сброс кода: `/student/{student_id}/credentials`, `/student/{student_id}/access_code`, после подтверждения admin-прав.
- Баланс, история, прогресс награды и рейтинг: существующие GET endpoints.
- Удаление аккаунта и отзыв сессий: UI без отсутствующих mutations. Блокировка/разблокировка ученика исключены полностью.

### Группы

- Список/фильтры: `/course`, `/group/course/{course_id}`; детали: `/group/id/{group_id}`; создание: `/group/create`.
- Преподаватели и состав учеников: существующие PUT/DELETE endpoints.
- Переименование, смена курса и удаление: UI без отсутствующих mutations.
- Массовые назначения/переводы: существующие операции с частичным результатом. При переводе сначала подтвердить добавление в целевую группу, затем удалить из исходной.
- Групповое начисление за практику: `/group/id/{group_id}/practice-completed`, без модели занятия/посещаемости.

### Курсы и категории

- Чтение/создание: `GET/POST /course`; связанные группы и фильтры категорий.
- Переименование, изменение категории и удаление курса: UI без отсутствующих mutations.
- `CourseCategory` — фиксированный enum; управление самими категориями — UI без отсутствующих mutations. Не создавать параллельные категории через метки.

### Баланс

- Баланс, история, рейтинг/позиция: существующие GET endpoints.
- Начисления/списания по причинам: `/student/{student_id}/balance/transactions`; сумму определяет backend.
- Отмена: `/student/transactions/{transaction_id}/cancel`.
- Массовые операции: выбор учеников, результат по каждому, повтор только однозначно неуспешных операций.
- Произвольная сумма и настройка причин/тарифов: UI без отсутствующих mutations; чтение причин через `/ext/balance/balanceChangeReasons`.
- Финансовую историю читать из API, не дублировать все транзакции в нашей БД ради журнала. Глобального endpoint нет; не выдавать историю одного ученика за общую историю системы.

### Стрик

- Самостоятельная функция в профиле ученика.
- Текущий/максимальный стрик, запуск, завершение, изменение дней через endpoints streak/longest-streak.
- Не связывать с расписанием, посещаемостью или групповыми начислениями; автоматические правила не придумывать.

### Каталог наград

- Список, фильтры, детали, создание: `/rewards`, `/shop/{reward_id}`, `POST /rewards`.
- Поля: название, цена, описание, тип (`reward`/`privilege`), категория или отсутствие привязки.
- Изменение базовых полей и удаление: UI без отсутствующих mutations.
- Каталог ещё не согласован и будет меняться: сделать полноценный UI добавления и управления наградами, не вводить дополнительные правила продукта. Перед реализацией сверить актуальный API; всё доступное подключать реально, отсутствующие изменения оставлять UI без мутации.
- Изображение: два доступных режима «Посилання» и «Вибрати файл», предпросмотр, замена и удаление выбранного изображения. Файл выбирается с телефона; без storage это локальный выбор, а не выполненная загрузка на сервер.
- В предоставленном контракте нет поля изображения и endpoint загрузки. Пока ссылка/файл остаются в состоянии формы, не отправляются в неподдерживаемые поля и не сохраняются через выдуманный backend. Storage выбрать позже.
- Создание самой награды через доступный `POST /rewards` выполняется реально с поддерживаемыми полями даже при отсутствии сохранения изображения. UI должен различать сохранённую награду и несохранённое изображение.
- Скрытие/доступность, редактирование и удаление: полноценный UI; реальные вызовы только при наличии соответствующего API. Не создавать `reward_metadata` и не менять ученический магазин ради обхода отсутствующих endpoints в этой версии.
- Никаких флоу выдачи, склада, покупки, возвратов или применения привилегий.

## Мобильные флоу

- Основные разделы: обучение, люди, каталог; баланс/операции и настройки — через меню. `/admin` открывает список групп.
- Список → поиск/фильтры → объект → действие → форма → результат.
- Регистрация → экран кода → профиль/список.
- Назначение/перевод → выбор → параметры → результат по объектам.
- Реальные операции: загрузка, пустое состояние, ошибки, повтор, серверная валидация и обновление query-кэша.
- Неподключённые операции: полноценный UI без записи выдуманного результата в серверные данные.

## Последовательность реализации после согласования

1. Вход, guards, мобильная навигация и настройки admin.
2. Преподаватели, ученики, группы, курсы: API-операции и UI недоступных действий.
3. Баланс, массовые действия, самостоятельный стрик и каталог.
4. Два режима изображения награды: ссылка/выбор файла и локальный предпросмотр; без backend загрузки до выбора storage.
5. Проверка мобильных флоу, прав, повторов, ошибок API и частичных результатов массовых операций. Новые таблицы БД создавать только при появлении согласованной функции, которой они нужны.

После изменений запускать `bun check`. Не создавать `.test` файлы в репозитории.

## Технические проверки и отложенные решения

- Дополнительных продуктовых ответов для начала реализации не требуется. Пользователь не управляет правами backend; не блокировать план требованием предоставить матрицу прав. Использовать роль admin и доступный контракт, корректно обрабатывать 401/403. Фактический запрет сервера нельзя обойти нашей БД или скрыть как успешную операцию.
- В интеграции самостоятельно проверить, какой идентификатор ожидает профиль преподавателя: ID аккаунта или ID профиля. Для назначения на группу контракт явно требует user IDs. Не перекладывать этот технический вопрос на пользователя.
- Схема допускает пустой `teacher_ids` (нет minItems), максимум два. UI может позволять оставить группу без преподавателя, но должен отображать серверную ошибку, если backend это запрещает. Не вводить выдуманное обязательное назначение.
- Изменение nickname реализовать по имеющемуся контракту, не придумывая дополнительное поле полного имени.
- Storage и окончательные правила наград отложены; сейчас оба варианта выбора изображения доступны в UI.
